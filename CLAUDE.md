# Lumber-CLI

`@infinitetoken/lumber-cli`: the `lumber` command, which reads Lumber logs in the terminal and serves them to AI agents over MCP, decrypted on the computer it runs on. Part of the Lumber suite (`../Lumber/CLAUDE.md` has the whole picture); the backlog entry it came from is `../Lumber/.planning/ROADMAP.md` Phase 999.1. Built 2026-10-29 for Chris, Lumber's first real user, ahead of launch: read-only, no `export` yet. macOS only until 0.3.0 (2026-11-09), which added Windows and Linux.

## Commands

```bash
npm run verify    # lint, test, typecheck, build
npm run build     # tsup into dist/cli.mjs (the bin)
node dist/cli.mjs help
npm run build:binary -- --node <nodejs.org's node 26>   # the standalone lumber for this computer, into release/
```

## CI

`binaries.yml` builds the standalone lumber on each system's runner and checks it (see Standalone lumber). `ci.yml` runs the shared `npm-ci.yml` (lint, test, typecheck, build on Linux) and a `test` job on macOS, Windows and Linux runners with `LUMBER_STORE_TEST=1`, which turns on `credentialStore.test.ts`: it saves, reads, replaces and removes a "Lumber CLI test" item in the runner's real store (never the session's own name). On Linux it first checks that `lumber status` with no Secret Service says so, then runs the tests under `dbus-run-session` with a GNOME Keyring unlocked by a throwaway password. `LUMBER_STORE_TEST=1 npx jest credentialStore` does the same against your own store (on a Mac, the login keychain, through `security`, so no prompt). A Linux container reproduces the Linux job: `node:22-bookworm`, `apt-get install gnome-keyring dbus`, then the same `dbus-run-session` line.

## Releasing

`npm run release:patch` (or `:minor` / `:major`): `preversion` runs verify, `npm version` tags, `release` pushes with tags, and the shared publish workflow (`infinitetoken/Workflows`' `npm-publish.yml`, the same `ci.yml` and `publish.yml` as Lumber-Node, Lumber-Kit and the rest of the fleet) publishes with npm's trusted publishing, no token. The repo is public since 2026-11-09, so npm attaches provenance. `npm version` also runs the `version` script (`scripts/server-json.cjs`), which sets `server.json`'s versions to the new one and stages it into the version commit.

Then, for each release:

- **Homebrew**: this repo is the tap (Jay, 2026-11-09: public already, so no separate tap repo). People run `brew tap infinitetoken/lumber https://github.com/infinitetoken/Lumber-CLI`, then `brew install infinitetoken/lumber/lumber`: Homebrew 7 refuses formulas from a tap nobody trusted, and installing by the full name is what trusts it (tapping doesn't). `Formula/lumber.rb` installs npm's tarball with `std_npm_args` and depends on node; its `test do` checks the version, an MCP `initialize`, and on Linux the no-Secret-Service message (which loads the keyring module). After each Publish run, `homebrew.yml` points it at npm's latest (`scripts/formula.sh`, the tarball's URL and sha256), has Homebrew install, test and audit it on macOS and Linux runners, and commits it to main as github-actions when the version changed. Nothing to do by hand; `gh workflow run homebrew.yml` runs it now. That commit lands after every release, so `preversion` pulls (`git pull --rebase`) before verify, and anything pushing to main should pull first. Homebrew's npm skips dependencies published in the last day (its release cooldown), so a release needing a brand-new dependency fails that run until the dependency is a day old: rerun it then. A lumber running from Homebrew's Cellar tells people to `brew upgrade lumber`.
- **GitHub Release** (since 2026-11-10, not yet run): the same tag runs `binaries.yml`, which builds the standalone lumber for six targets, checks each, and makes the tag's GitHub Release with the archives, `SHA256SUMS` and a build provenance attestation. Nothing to do by hand.
- **Scoop**: this repo is also the bucket (`bucket/lumber.json`, written by `scripts/scoop.mjs` from the release's `SHA256SUMS`). After each tagged Binaries run, `scoop.yml` writes it, has Scoop add this checkout as a bucket and install it on `windows-latest` and `windows-11-arm`, runs it through Scoop's shim (version, help, MCP) and the Credential Manager round trip, and commits it to main. `bucket/` doesn't exist until the first release with binaries. Nothing to do by hand.
- **winget** (`InfiniteToken.LumberCLI`, moniker `lumber-cli`): after each tagged Binaries run, `winget.yml` writes the version's three manifests (`scripts/winget.mjs`, schema 1.12.0, a portable `lumber.exe` in each Windows zip) as an artifact and, when the repo has a `WINGET_TOKEN` secret, sends them to `microsoft/winget-pkgs` with Komac (`komac submit`, pinned by `KOMAC_VERSION` and checked against its `SHA256SUMS`). Microsoft's checks and a moderator take it from there, usually a day or two. Until the secret exists it stops after the manifests. See Windows: what Jay does.
- **MCP Registry** (`com.infinitetoken/lumber`, `mcpName` in package.json, which the registry checks against npm): `mcp-publisher login dns --domain infinitetoken.com --private-key "$(security find-generic-password -s 'MCP Registry' -a infinitetoken.com -w)"`, then `mcp-publisher publish` from this folder, after npm has the version. The key is Ed25519, kept only in Jay's login keychain ("MCP Registry" / infinitetoken.com); its public half is the `v=MCPv1; k=ed25519; p=...` TXT record on infinitetoken.com's apex at DNSimple. A new key means a new TXT record (and removing the old one). `mcp-publisher validate` checks `server.json` first.

The first publish (0.1.0) has to be by hand, from Jay's Mac (`npm publish`, with his npm 2FA): npm only lets a package that already exists name a trusted publisher. Then on npmjs.com, the package's settings, Trusted Publisher: GitHub Actions, `infinitetoken` / `Lumber-CLI`, workflow `publish.yml`.

package.json has no `os` field: it runs on macOS, Windows and Linux, and `credentials.ts` says so anywhere else (`UNSUPPORTED`).

## Layout

- `cli.ts`: the bin's entry, nothing else. `commands.ts`: termkit's `Program` (commands, options, help), spinners and output, and `runCommand(argv)` giving the exit code (2 for a mistake on the command line, 1 otherwise).
- `session.ts`: the session in the credential store (`credentials.ts`), `request` (fetch to the API, a 401 with a token is `NotSignedInError`) and `openClient`, which reads the store each time and trades a token over a day old for a fresh one (`POST /token/refresh`), as the apps' `useSessionKeeper` does.
- `credentials.ts` (since 0.3.0; `keychain.ts` before): the session in the system's own credential store, always service "Lumber CLI", account "session", never a file. `storeFor(platform)` picks:
  - macOS, `keychainStore`: a generic password (base64 of the session JSON) through `/usr/bin/security`, as before 0.3.0, so Jay's and Chris's logins carried over untouched. Written with `security -i` reading its command from stdin, so the secret never shows in the process list. An item `security` creates trusts `security` (Apple signed, so its designated requirement survives macOS updates), so reads never prompt. A native module stays off the Mac on purpose: an item it creates trusts node, and Homebrew's node is signed ad hoc (`codesign -d -r-` gives `cdhash H"..."`), so every `brew upgrade node` would bring the Keychain prompt back, and reading the existing items would prompt once too.
  - Windows and Linux, `keyringStore`: `@napi-rs/keyring`'s `AsyncEntry`, imported only there, so a Mac never loads the native module. UTF-8 bytes through `setSecret`, since Windows keeps a password as UTF-16 in a blob of at most 2,560 bytes. Windows names it `session.Lumber CLI` (the store's `user.service`), with the store's default Enterprise persistence, which roams only on a domain with roaming profiles; neither store trusts by binary, so a node upgrade prompts nothing. Linux pins `{ linux: { store: 'secret-service' } }`: left to choose, the module falls back to the kernel keyring, which forgets at reboot. The Secret Service connects when the entry is made, so a Linux with none fails there, as `StoreUnavailableError` with `NO_SECRET_SERVICE` (exit 1, no stack).
  - `THIS_COMPUTER` (constants.ts) is "this Mac" on macOS and "this computer" elsewhere, and `storeName` names the store in messages.
- `embeddedKeyring.ts` and `nativeLibrary.ts` (since 2026-11-10): `@napi-rs/keyring` in the standalone lumber, which `scripts/sea.mjs` aliases in for the package. The native library is an asset of the executable; `placeNativeLibrary` writes it to `lumber-cli/keyring-<hash>.node` in the cache folder (only when the file there doesn't already hold exactly those bytes, so a damaged one is written again), removes other versions' libraries, and `process.dlopen` loads it. Imported only on Windows and Linux, as the package is.
- `crypto.ts`: Node's own crypto, no noble: X25519 keys as raw 32 bytes in base64, wrapped in fixed DER prefixes for Node; `unwrap` is the apps' ECIES (sender key, IV, tag, ciphertext; HKDF-SHA256, info `lumber-v1`, empty salt, which equals noble's undefined salt); `decryptWire` is AES-GCM with the tag first. `crypto.test.ts` checks both against vectors from the plugin and the app's own noble code.
- `login.ts`: sign in, then link as a device, as the phones' Link This Device does (since 2026-10-29, 0.1.1 showed a QR of the long code instead): a one-off keypair, `POST /device-links` (`platform: 'cli'`), then a `Code` prompt for the 7 digits a device holding the account key shows (it asks again for a typo, which the check digit catches, or when no device is showing a code for the request yet), the answer (`POST /device-links/:id/answer`, the answer alone: the secret the code gave stays here), polling every 3s until approved, failed (a wrong code, which ends the request) or denied, and two checks on the key that came back before anything is saved: its `deliveryTag` was made from that secret, so a device that showed the code sent it and not the server (since 2026-10-30), and it's the account's (its public half equals `/me`'s `publicKey`). A 409 on the answer means someone else answered the request, whose key couldn't be checked, so it stops there. The same person signing in again keeps the stored key. The CLI no longer shows the long code, so the device showing the code needs the 2026-10-29 app.
- `linkCode.ts`: the new device's half of the apps' link exchange (Lumber's `linkExchange.ts` over `keyCheck.ts`: CPace on ristretto255, DST `lumber-device-link-v1`, bound to the request id and user id, lowercased), with the code's Damm check digit. It only answers and checks the tag on the key that comes back (`deliveryChecksOut`), so it needs only the generator, the shared secret and the two tags. Node's crypto has no ristretto255, so it uses `@noble/curves` and `@noble/hashes`, which ship only ES modules: `jest.config.cjs` has ts-jest compile them (`allowJs`, `transformIgnorePatterns` letting `@noble/` through), since Jest can't require them on Node 22. `linkCode.test.ts` pins its answer to a request Lumber's own code started (`exchangeVector.test.ts` there checks the same answer with its `verifyLinkAnswer`) and checks the tag Lumber's code makes for it, as does Lumber-Worker's demo code, so change all three together.
- `apps.ts`, `logs.ts`: apps with their keys unwrapped; log search (newest first, paging back, text matched locally up to `DEFAULT_SCAN` logs) and `logsSince` (forward, for catching up).
- `tail.ts`: `followLogs`, the socket (`listMyApps` says which apps stream live) plus polling every 5s for the rest, catching up from the newest log seen (less 5s, ids weeding out repeats) on every connect.
- **Monthly logs** (2026-11-13): each app carries `logsCappedUntil` (its team is past its plan's monthly logs, so Lumber-API takes only ERROR and FATAL) and `logsStoppedUntil` (at twice them, nothing), from the API's app records. `lumber apps` notes `monthly limit reached: errors only until ...` (warn color) or `logs refused until ...` (error color), `--json` and MCP's `list_apps` carry both. Needs Lumber-Kit 1.0.0 for `logsStoppedUntil` on `AppRecord`.
- `mcp.ts`: `list_apps`, `search_logs`, `wait_for_logs` (polls `logsSince`, groups by app, level and message, returns `next_after` a millisecond past the newest) and `list_notes`, all read-only. Every tool and the server's instructions say log text is untrusted data.
- `update.ts` (since 0.2.2): the update notice. `runCommand` starts `startUpdateCheck` before a command and calls its `finish` after, which writes the notice to stderr. It fetches `registry.npmjs.org/@infinitetoken/lumber-cli/latest` (about 3 KB, 0.2s) when the last check is a day old, in parallel with the command, and `finish` aborts a check still running rather than waiting, so a command never takes longer (a fast one like `--version` just drops it and asks next run). The answer, when it last asked and when it last said so live in `lumber-cli/update.json` in the system's cache folder (`cacheDir`: `~/Library/Caches`, `%LOCALAPPDATA%`, or `$XDG_CACHE_HOME` or `~/.cache`); the notice shows at most once a day. How to update follows how it was installed (`howInstalled`): `brew upgrade lumber` when lumber runs from Homebrew's Cellar (`installedWithHomebrew`, the real path of `argv[1]`) and `npm install -g` otherwise; in the standalone lumber (`STANDALONE`, set at build time), `scoop update lumber` from Scoop's `scoop\apps\lumber`, `winget upgrade InfiniteToken.LumberCLI` from winget's `WinGet\Packages\InfiniteToken.LumberCLI_*` (the real path of `process.execPath`: winget's `lumber` is a link to it), and the release page otherwise. It still asks npm which version is latest, so a winget install hears of a release a day or two before winget has it. Only at a terminal (stderr is a TTY), never for `mcp` (stdio is the protocol) or `tail` (runs until Ctrl-C, which termkit exits on), under `CI`, or with `LUMBER_NO_UPDATE_CHECK`. A prerelease never reads as newer. Jay's own `lumber` is linked to this checkout, so it reports this checkout's version.

## Standalone lumber (2026-11-10)

winget and Scoop want a program, not an npm package on a Node of the person's own, so `scripts/sea.mjs` builds lumber as a Node single executable application: the CLI bundled into one ES module (tsup, every package inside, `node:` prefixes kept since `node:sea` exists only by that name), injected into a whole Node 26 with `node --build-sea` (Node's own since 25.5, no postject), with the code cache compiled in when the target's Node can run there. Chosen over `bun build --compile` because it's the same runtime npm and Homebrew users run (socket.io, the MCP SDK, termkit and X25519 behave the same), so there's no second runtime to test. The cost is size: the executable is Node's binary plus 2 MB, 88 to 148 MB, 34 to 47 MB packed. It starts faster than npm's (0.17s against 0.64s for `--version` on an M-series Mac).

- **`sea.mjs build|pack`**: `build` writes `build/sea/<target>/` (the executable, `LICENSE`, `THIRD-PARTY-NOTICES.txt`), `pack` archives it to `release/lumber-<version>-<target>.zip` (Windows) or `.tar.gz`, files at the top; left out, it does both. CI checks between the two, which is where Windows signing goes. Targets: `windows-x64`, `windows-arm64`, `linux-x64`, `linux-arm64` (glibc, as Node's own binaries), `macos-arm64`, `macos-x64`. `--target` and `--node` build another system's here, without a code cache; the keyring package for it comes from `npm pack`.
- **The Node must be whole**: nodejs.org's or setup-node's. Homebrew's `node` is a 132 KB launcher for its `libnode` dylib, and the script refuses it.
- **Licenses**: the archive carries Node's `LICENSE` (found beside its binary) and every bundled package's license file, from esbuild's metafile, plus the keyring's Rust crates (`LICENSE.third-party.md`). A package with no license file fails the build.
- **`execArgvExtension: 'none'`**: Node reads `NODE_OPTIONS` in a SEA by default, so a developer's `--require` for their own project crashed lumber before it started. `check-binary.mjs` keeps it fixed.
- **Archives from a Mac**: macOS's tar added `._` files and xattr headers that Linux unpacks as clutter (`COPYFILE_DISABLE`, `--no-xattrs`, `--no-mac-metadata` now). On Windows the zip is made by `System32\tar.exe` (bsdtar): Git Bash puts GNU tar first, which can't write one.
- **macOS**: signed ad hoc (Apple silicon runs nothing unsigned). Not notarized, so a browser download runs only after `xattr -d com.apple.quarantine lumber`, which the README says; Homebrew stays the Mac's way. Developer ID and notarization through jrd would fix it if Mac downloads matter. Node's docs only test SEA on arm64 Macs; the x64 build ran under Rosetta here.
- **CI's check** (`binaries.yml`, each target on its own runner: `windows-latest`, `windows-11-arm`, `ubuntu-latest`, `ubuntu-24.04-arm`, `macos-latest`, `macos-15-intel`): `check-binary.mjs` (version, `NODE_OPTIONS` ignored, help showing `claude mcp add lumber -- lumber mcp` with no `cmd /c`, an MCP `initialize`), on Linux the no-Secret-Service message, and `LUMBER_STORE_CHECK=1 lumber`, which saves, reads, replaces and removes a "Lumber CLI test" item in the real store and does nothing else (`checkStore` in `credentials.ts`; it ships in every build, inert without the variable). On a tag, the `release` job makes the GitHub Release.
- **Checked here before any CI run** (2026-11-10): macOS arm64 and x64 (Rosetta) against the login Keychain, with `status`, `logs` and MCP against Jay's account. Windows arm64 and x64 (Prism) in the Windows 11 ARM VM: the Credential Manager round trip, help, MCP; then a real `winget install --manifest` (manifests validated by winget 1.29) and a real Scoop install, each run through its link or shim, MCP included with no shell, and winget's real path matching `howInstalled`. Linux arm64 in the Ubuntu 26.04 VM: the no-Secret-Service message and the round trip in GNOME Keyring, the extracted library needing only libc. The VMs ran disposable (`utmctl start --disposable`, QEMU `-snapshot`), so nothing stuck. Not run anywhere yet: linux-x64, and the native builds in CI (`binaries.yml`, `scoop.yml` and `winget.yml` run on the first push).
- **Windows over SSH**: Credential Manager refuses a key-based SSH session (`ERROR_NO_SUCH_LOGON_SESSION`, no credentials in that logon), so the VM check ran as a scheduled task in the signed-in desktop session. GitHub's runners have a full logon.

## Windows: what Jay does

1. **Release as usual** (`npm run release:minor`). The binaries, the Scoop bucket and the winget manifests follow by themselves. Then pull: `scoop.yml` and `homebrew.yml` both commit to main.
2. **winget's first version, by hand**: on the Actions page, the winget run's `winget-manifests` artifact (or `node scripts/winget.mjs`, which reads the latest release, into `build/winget`). Then `brew install komac`, `komac token add --token "$(gh auth token)"` and `komac submit build/winget/manifests/i/InfiniteToken/LumberCLI/<version>`: Komac forks `microsoft/winget-pkgs` under Jay's account and opens the pull request. A first package gets a moderator's look, a few days.
3. **winget after that**: a classic token with the `public_repo` scope (fine-grained tokens can't open the pull request) as the repo's `WINGET_TOKEN` secret, and each release submits itself. Without it, repeat step 2 per release. Once winget has it, add `winget install InfiniteToken.LumberCLI` to the README and Lumber-WWW's CLI page.
4. **Signing (not needed for winget or Scoop, both checked unsigned)**: an unsigned `lumber.exe` gets SmartScreen's warning only when a browser's download is opened from Explorer, but Smart App Control blocks it outright, and managed Windows can refuse unsigned programs. Microsoft's own answer is Azure Artifact Signing (formerly Trusted Signing): about $9.99 a month (Basic, 5,000 signatures), open to organizations in the US, Canada, the EU and the UK, so Infinite Token LLC, and not on a free or trial Azure subscription. Steps: an Azure pay-as-you-go subscription; register the `Microsoft.CodeSigning` resource provider; create an Artifact Signing account (Basic, a US region, which gives its endpoint, `https://eus.codesigning.azure.net/` for East US); give your own user the Artifact Signing Identity Verifier role on it; a Public identity validation for Infinite Token LLC (legal name and address as registered, EIN or a D-U-N-S number, emails on the company's domain; whoever can show the LLC's papers does it, through AU10TIX and Microsoft Authenticator; a few business days); a Public Trust certificate profile on that identity; then an app registration with a federated credential for this repo's GitHub Actions (no secret), given the Artifact Signing Certificate Profile Signer role. Its client, tenant and subscription ids, the endpoint, the account name and the profile name go in as repo variables, and `binaries.yml` gets, for the Windows targets between `build` and the checks, `azure/login` (OIDC) and `azure/artifact-signing-action@v2` on `build/sea/<target>/lumber.exe` with Microsoft's timestamp server. Reputation builds with each signed release under the same identity; signing doesn't remove the first warnings. Certificates last three days and renew themselves; signed files stay valid. SignPath Foundation signs open source for free, under its own name rather than Infinite Token's.

## termkit

The CLI is on Jay's `termkit` (Program, input, Spinner, Table, markup, Color). It writes everything to stdout, so:

- `lumber mcp` must never touch a Spinner, `log` or Table: stdout is the MCP protocol there.
- Spinners stop without a message. Spinner draws nothing when stdout isn't a terminal, but its completion messages would still land in piped or `--json` output.
- `tail` in a terminal keeps a Spinner as a status line and prints logs above it with `spinner.log(line, '')`; piped or `--json`, logs go straight to stdout and the state to stderr.
- termkit treats `help` or `version` anywhere in argv as asking for them, so `lumber logs -g help` prints help. `-g Help` searches (the match ignores case).
- termkit's color module calls `process.exit()` on SIGINT; `tail` uses `prependOnceListener` to clear its status line first.
- termkit 2.4.12's parse errors still carry an em dash (`Invalid value "abc"`, then the dash, then `expected an integer`); TermKit's main has the fix, unreleased as of 2026-10-29.

## Colors

The apps' look, from Lumber-Kit: level colors (`logLevelColors`), each app's name after a square in its own color (`resolveAppColor`: its color, or its name's; the color is on the square, not the name, since most app colors are about 2:1 on a light terminal's white), and your accent for the spinner (breathing into a shade a quarter darker), help, tables and prompts (`useAccent`, through termkit's `configure`). Your accent is `/me`'s `color`, saved in the session at sign-in, at each daily token refresh and by `lumber status`, and read by `runCommand` before anything draws; amber (`DEFAULT_ACCENT`) without one. `live` is the green of the apps' connection dot, connecting amber, trouble red.

The colors and name hash are Lumber-Kit's since 0.5.2 (`^0.5.2` here); the app re-exports the same ones, so an app is the same color in both.
